## Debugging changes made to the phone (revert at end of session)
1. `sleep-inactive-{battery,ac}-type` set to `'nothing'` via the phoc session bus, so the
   phone stops idling into suspend and the cable stays up. This is what keeps USB alive;
   it must be restored (`'suspend'`) before suspend work is re-verified.
2. `/etc/elogind/system-sleep/no-hexagonrpcd-on-suspend.sh` **moved to `/root/sleep-hook-off/`**.
   It was moved during a failed "keep the cable alive" attempt. It was NOT the cause of the
   cable drops (the link still dropped 71 s after enumeration with the hook already gone).
   Move it back to re-arm suspend, but note that its `post` step only rebinds the UDC if
   `/run/violet-sleep-udc` is non-empty, so a resume can leave the gadget unbound — that is a
   real bug in the hook and needs fixing in the hook, not in dwc3.

## Item 2 (modem / WiFi) — narrowed by measurement today
On this boot the failure repeated every 40.03 s and never produced `wlan0`:
```
 26.24  remoteproc1: powering up modem      27.44  remote processor modem is now up
 67.47  fatal error without message         (== 40.03 s after "now up")
 68.08  up again   108.11 fatal  108.76 up again  ...
```
Evidence that the glink transport is fine (trace ring, `trace_event=qcom_glink,...` is in the cmdline):
```
27.438  qcom_glink_cmd_version_ack  tx/rx remote: mpss version: 1
27.443  qcom_glink_cmd_open        rx remote: mpss channel: IPCRTR[0/1]
27.443  qcom_glink_cmd_open_ack    tx remote: mpss channel: IPCRTR[0/1]
27.443  qcom_glink_cmd_open    tx / open_ack rx  remote: mpss channel: IPCRTR[1/1]
27.444  12x qcom_glink_cmd_intent  rx remote: mpss channel: IPCRTR[1/1] size 128 liid 0..11
481 glink events mention `remote: mpss`; 0 glink errors.
```
But QRTR sees nothing from it: `qrtr-lookup` has **no Modem node** (node 1 = AP: 14 rmtfs,
64 pd-mapper, 4096 TFTP; node 5 = ADSP: 769/400/43/66/51/24), and the `qrtr_ns_message`
trace contains **only** `new-lookup from 1:16405` (the AP itself) — no HELLO, no NEW_SERVER
from any remote node, over the whole boot.
So: `qcom_smd_qrtr` is bound to `4080000.remoteproc:glink-edge.IPCRTR.-1.-1`, the channel is
open both ways, and the name server still never learns about the modem. Two remaining
possibilities, and they are separable without a reboot:
  (a) mpss never transmits its QRTR HELLO after `open_ack`;
  (b) it does, and `qcom_smd_qrtr`/af_qrtr drops it before `qrtr_ns`.
Next measurement: instrument the rx side of that one channel (packet counter + first 16 bytes
of each rx skb) and re-read the trace from the same boot; do **not** reboot to test it.
Killed hypotheses today: "glink open handshake never completes" (open/ack are clean);
suspend hook causing the USB drops (drops persisted without it).

## Staged, NOT applied to the phone (userspace only, no kernel change)
- `phone/violet-modem.initd` — `stop()` now waits (bounded 15 s) for the remoteproc to report
  `offline` before returning, so rmtfs is not torn down under a modem still writing EFS; the
  background retry loop checks `/run/violet-modem.stopping`, so it can no longer write `start`
  back into the modem during shutdown. Observed on the phone today: a manual stop took
  0.6 s (`147.87 modem stopping` -> `148.43 offline`), so the wait is cheap.
- `phone/hexagonrpcd-adsp-sensorspd.initd` — `retry="SIGTERM/3/SIGKILL/2"`. From
  supervise-daemon.c: `--stop` signals the supervisor and then waits in an untimed
  `while (kill(pid,0)==0)` loop, and `retry` is the only schedule there is (default
  `SIGTERM/5`, no escalation). Question this answers: whether that is the shutdown hang.
- `host/shutdown-test.sh` — one command that enables `rc_logger`, streams `dmesg -wT` on the
  laptop, reboots, waits for WiFi or USB, then pulls `/var/log/rc.log` + pstore.
